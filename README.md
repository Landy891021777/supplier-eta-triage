# Supply Chain AI Tool: Delivery Risk Prioritization

**供應鏈 AI 工具：交期風險優先排序**

給**晶圓廠物料企劃**用的內部工具。每天早上收到一批供應商的交期回覆信，
格式各異、中英夾雜、措辭模糊。這個工具把信讀懂、對回採購單的交貨排程行，
算出**預估缺料天數**，排出今天該先追哪幾張，每一張都附理由與建議動作，
並讓企劃在同一個畫面看到**這家供應商過去說話算不算數**。

> ⚠️ **誠實聲明**：本專案全部使用**合成資料**，未使用任何公司的真實資料，也未串接真實 ERP。
> 真實的採購單與交期屬營業秘密，因此以程式產生資料，並把領域假設寫成可逐條檢視的程式碼
> （見 `src/generate_data.py`、`src/generate_history.py` 的 `# 領域假設：` 註解）。
> 文件中的數字都由程式實際跑出來；合成資料上的數字只能證明程式邏輯自洽，不能證明真實環境有效。

## 功能一覽

| 模組 | 做什麼 | 關鍵設計 |
|---|---|---|
| **① 讀信** | 把回覆信轉成「哪張單、哪一批、新交期、有沒有承諾」 | 規則先讀，沒把握才交給 LLM；一封信可抽出同一張單的多批交期 |
| **② 排序** | 排出今天該先追的採購單 | 預估缺料天數＝兩個日期相減；P1／P2／P3 只看事實，沒有權重 |
| **③ ERP 與歷史** | 從模擬 ERP 算出供應商說定日期後通常還晚幾天 | 10 張表，結構參考 SAP MM；企劃的調整與確認存工具自己的資料庫，不寫回 ERP |
| **④ 物料智能檢索** | 用平常講話的方式查採購單、料號、供應商與工具說明 | 語意檢索＋單號料號直接取出；每句話標出處，並檢查出處真的存在 |

```
供應商回覆信
    │
    ▼
① 讀信   規則層（免費、可重現）──沒把握──► LLM 層
    │      同時判斷承諾強度：已確認／暫估／僅意向
    ▼
② 排序   對到採購單的交貨排程行 → 預估缺料天數 → P1／P2／P3 ＋ 建議動作
    │      不是「已確認」的日期：標「需人工確認」，不當成排程依據
    ▼
③ 歷史   模擬 ERP 的收貨紀錄 → 這家供應商說定日期後還晚幾天 → 保守到料日
    │      同一批歷史再拿來做時間切分回測
    ▼
④ 檢索   「PO-2026-04205 的供應商可靠嗎？」→ 附出處的回答
```

## ① 讀信：規則先讀，沒把握才交給 LLM

一天幾十到幾百封信全部送 LLM，成本、延遲都讓人不想用，結果也無法重現。
所以先用程式規則解析（多種日期格式、欄位標籤、表格同列比對、「照原計畫」等反向語意），
**規則層判斷自己沒把握（信心 < 0.75）才升級呼叫 LLM**：相對日期、轉寄串、一封多單、模糊措辭。

**承諾強度是這一層最重要的欄位。**
供應商寫「大概月底吧，我再跟你確認」—— 若工具把它抽成 `2026-10-31` 填進表格，
企劃會以為事情定了。所以解析時必須同時判斷這句話算不算承諾：

| 判定 | 例句 | 工具的處理 |
|---|---|---|
| 已確認 | 「Revised ETA 10/30, confirmed」 | 可作為排程依據 |
| 暫估 | 「around Oct 20 but not yet locked」 | 標「需人工確認」，保守到料日取更保守的百分位 |
| 僅意向 | 「我們盡量」「cannot commit a firm date」 | 標「需人工確認」，**不可**作為排程依據 |

**分批交貨**：供應商常回「8 片照原日期出，剩下 12 片延到 11/15」。
這種信會抽成兩筆，各自帶數量與日期；照原日期那批判為「不變」，延後那批判為「延遲」。

LLM 的 prompt 會帶入系統裡的原承諾日。供應商寫「往後兩週」時，信裡並沒有原本是哪天 ——
那個資訊在我方系統，不給模型就是要它猜。

## ② 排序：兩個日期相減，每一步都能驗算

```
預估缺料天數 = 保守到料日 + 收貨處理天數 − 下游需求日
保守到料日   = 供應商說的日期 + 這家供應商過去「改期過的單」實際又晚了幾天（歷史百分位）
收貨處理天數 = 料到廠後，進料檢驗、入庫要幾天才能投產（仿 SAP 料號主檔 MARC-WEBAZ）
```

正數是預估缺幾天，零或負數是還有幾天緩衝。這是兩個日期相減，可以在缺料檢討會上逐項驗算，不是分數。

**承諾強度決定取哪個百分位**：已確認 P80、暫估 P90、僅意向或沒給日期 P95。
這三個數字是領域假設（`config.yaml` 的 `triage`），回測只能檢驗涵蓋率，不能證明它們「對」。
歷史只用改期過的單，因為企劃收到的是已經跳票的通知；改期單少於 20 張的供應商退回全部單並標明，
全部單也不足就不給估計。

**收貨處理天數**依料別預設（光阻 2 天：冷藏品開瓶前要回溫一晚；光罩 3 天：要驗證曝光；
其餘 1 天）。查不到半導體業依料別的公開天數，這組數字是依到廠作業步驟推得的假設；
企劃可在工具內逐料號調整，必填原因與姓名，每次調整都有紀錄。

**分級只看有沒有缺料與三個事實，沒有任何權重：**

| 分級 | 條件 |
|---|---|
| 🔴 P1 | 預估缺料，**而且**下游已排定產能或是瓶頸料 |
| 🟠 P2 | 預估缺料但不屬 P1；或單一來源、緩衝只剩 3 天內；或供應商說會延卻沒給日期 |
| 🟡 P3 | 其餘（有緩衝，或有已認證二源可轉單） |
| ⚪ 待查 | 讀不出新日期或變更內容，不拿原承諾日硬算 |

每一張都能展開看到理由，例如「供應商說 10/09；這家供應商過去改期過的單有 80%
在說定日期後 11 天內到，保守到料日 10/20；加上收貨處理 1 天，可投產日 10/21；比需求日晚 16 天」。

**分批交貨每一批各自追蹤、各自分級。** 追蹤單位是「採購單 × 交貨排程行」，不是整張單：
先到的那批準時、延後的那批缺料，清單上只會列出延後那批，而不是整張單缺料。
例如 PO-2026-04188（手寫案例 HC-010）：8 片照原日期、12 片延到 11/15，清單只列那 12 片，排 P1。
信中沒講是哪一批時，依序用數量、原日期比對排程行；都對不上時對到最早未交的一批，
並標「需人工確認」—— 寧可多問一次，也不要把日期套到錯的批次。
供應商在信裡提議把 ERP 的單一排程行拆成兩批時，兩批各自成列，理由寫明「ERP 的交貨排程行尚未拆行，請確認後由採購維護」，並標「需人工確認」。

**建議動作只寫物料企劃自己能做的事**，並遵守合格供應商名單（AVL）：
追日期、通知生管、請品保（IQC）優先安排進料檢驗、與採購確認能否向已認證二源詢價；
替代料只寫「請品保確認是否已通過驗證」，未確認前不寫成可用。成本與可行性資料庫裡沒有，不寫。

**企劃確認交期**：暫估或僅意向的單，企劃打電話要到確切日期後在工具裡登錄（日期、備註、姓名），
清單立刻改用這個日期重算。確認綁在當時那封信上，供應商又寄新信時舊確認自動作廢並明講。
這些紀錄存在 `data/planner_settings.db`，**工具永不寫回 ERP、永不自動寄信**。

目前的結果（52 封信）：

| 模式 | 自動濾除「確認不變」 | 行動清單 | P1 | P2 | P3 | 待查 | 需人工確認 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 開 LLM（雲端展示，讀種子快取） | 9 | 47 | 21 | 17 | 9 | 0 | 20 |
| 只用規則層（沒有金鑰） | 13 | 43 | 15 | 13 | 3 | 12 | 18 |

沒有金鑰時，規則層讀不懂的 12 封信列為「待查」請人看原信，而不是猜一個日期。

## ③ ERP 與歷史：供應商說的話能信幾分

以 SQLite 建立 10 張資料表，結構參考 SAP MM 的公開資料整理（非任何公司實際結構）：

```
vendor_master (≈LFA1)    material_master (≈MARA/MARC)   material_alternate
source_list (≈EORD)      purchase_req (≈EBAN)           po_header (≈EKKO)
po_item (≈EKPO)          po_schedule (≈EKET)            po_change_log (≈CDHDR/CDPOS)
goods_receipt (≈MKPF/MSEG)
```

資料量：14 家供應商、40 個料號（7 類晶圓廠生產用料）、260 張在途採購單
（297 筆交貨排程行，其中 37 張在 ERP 已拆成兩批）、1494 張已收貨的歷史單。

工具需要的判斷依據，**有好幾項在 ERP 裡沒有現成欄位**，必須用 SQL 推導：
承諾日在交貨排程行、需求日在請購單、改期次數要數變更文件、有無二源要數來源清單的合格供應商、
「說定日期後通常還晚幾天」要從收貨紀錄算。欄位對應見 [`docs/ERP欄位對應.md`](docs/ERP欄位對應.md)。

「供應商績效」頁另有**月度績效**（依承諾月份）：一個月少於 5 筆標「樣本不足」不給比例；
已過承諾日還沒收貨的單算作延遲並另列筆數，否則最近一兩個月的準交率會虛高。

## ④ 物料智能檢索（RAG）

用平常講話的方式查詢，例如「哪些料缺了沒辦法找別家救？」「PO-2026-04205 的供應商可靠嗎？」

**切塊**：結構化資料一個實體一張卡（一張採購單被切兩半就沒用了）；文件依標題切並補上出處。
另建**摘要卡**處理排名類問題 —— 檢索只會撈出幾張相似的卡，做不了「14 家裡誰最差」這種比較。

**檢索**：語意檢索＋識別碼釘選。問題裡出現單號、料號時直接取出，
並沿關聯多取一層（採購單 → 它的料號與供應商），因為答案常常不在被點名的那張卡上。

**回答**：只能根據檢索到的資料回答，每個事實標出處。
程式另外**檢查模型引用的出處是否真的有給它** —— 開發時第一次試跑就抓到模型引用了沒撈到的卡片。
資料裡沒有的（例如真實公司名稱），會直接回答沒有。

## 評估：每個設計決定都要有證據

三份報告在 `output/`，介面「🧪 方法驗證」頁可直接查看。評估必須容許推翻原本的假設，沒贏的地方照實寫。

### 回測：保守到料日準不準、排序有沒有比簡單做法好

時間切分回測（`src/backtest.py`，不需金鑰）：每張測試單只用「收到改期通知那天以前已收貨」的歷史，
不偷看未來。測試期 229 張改期過的單，其中 19.7% 實際缺料。

| 百分位 | 預期涵蓋率 | 實際涵蓋率 |
|---|---:|---:|
| P80 | 80% | 81.2% |
| P90 | 90% | 87.3% |
| P95 | 95% | **90.0%** |

| 排序方法 | 前 20% 命中率 | AUC |
|---|---:|---:|
| 本工具：預估缺料天數 | 37.4% | 0.770 |
| 基準 A：只看供應商說的日期 | 37.4% | 0.769 |
| 基準 B：只看供應商過去準交率 | 21.7% | 0.511 |
| 隨機 | 19.7% | — |

- **本工具與「只看供應商說的日期」打平**：命中率差的 95% 區間 [−12.9%, 11.1%] 跨過 0，
  這批測試單分不出高下，因此不宣稱贏。
- **P95 涵蓋率 90%，低於預期**，代表估計偏樂觀。可能原因之一是供應商表現隨時間變差，
  而估計用的是整段歷史；這是「只看歷史統計、不做預測」的已知代價。
- 歷史收貨紀錄沒有承諾強度，回測一律用 P80；現場依承諾強度選 P80／P90／P95 的部分沒有被驗證到。
- 報告的結論句依實際數字產生，不寫死。

### 解析：這裡到底需不需要 LLM？

52 封人工標註答案的信件，依書寫風格分群，規則層與 LLM 層各跑一次（`src/evaluate.py`）。
除了日期與承諾強度對不對，另外算「**誤判為已確認**」的筆數：供應商沒承諾卻被判成已確認，
日期會被當真、也不會要求人工確認，這是本工具最不能犯的錯。

| 信件風格 | 封數 | 日期正確（規則→LLM） | 承諾強度正確（規則→LLM） | 誤判為已確認（規則→LLM） |
|---|---:|---|---|---|
| 格式化通知 | 16 | 1.00 → 1.00 | 1.00 → 1.00 | 0 → 0 |
| 半格式化 | 10 | 1.00 → 1.00 | 1.00 → 1.00 | 0 → 0 |
| 確認不變 | 5 | — | 1.00 → 1.00 | 0 → 0 |
| 口語敘述 | 11 | 0.00 → 0.64 | 0.73 → **0.27** | 0 → 0 |
| 手寫刁鑽案例 | 10 | 0.44 → 0.89 | 0.48 → 0.90 | **3 → 0** |

- **格式化、半格式化、確認不變的信，規則層已經全對，不該送 LLM**：省成本、省時間，結果可重現。
- **手寫刁鑽案例是 LLM 的主要存在理由**：規則層有 3 筆把沒承諾的日期判成「已確認」，LLM 降到 0；
  日期正確率 0.44 → 0.89。
- **口語敘述信，LLM 有得有失**：日期從規則層完全抽不到變成 0.64，但承諾強度反而比規則層差
  （0.27 對 0.73）—— 模型把「大概、左右」這類有保留的日期判成「僅意向」（標準答案是「暫估」）。
  這種錯仍會標「需人工確認」，並取更保守的 P95，不會讓日期被當真；兩層的「誤判為已確認」都是 0。
- **與上一版相比退步了**：為了支援分批交貨，提示詞加了一節說明與範例；加了之後，口語敘述信的 LLM 日期正確率
  1.00 → 0.64、承諾強度 0.55 → 0.27（手寫案例則小幅進步）。錯的日期是跨年算錯年份
  （2027-01 變成 2026-01）、「下個月中」算成本月、「下個月底」沒給日期。
  **沒有回頭調提示詞**：用同一批題目調到分數變好，等於看了答案再改考卷。
  比較根本的做法是模型只抽「往後 6 週」「下個月底」這類原文、日期由程式依原承諾日計算，列為下一步。

信件的風格比例是資料產生器設定的，因此不宣稱「幾成信件不需 LLM」這種比例。

### 檢索：評估推翻了原本的設計

24 題（作者撰寫）、知識庫 397 張卡片、六種檢索配置（`src/rag/evaluate_rag.py`）：

| 配置 | Hit@1 | Hit@3 | MRR |
|---|---:|---:|---:|
| 純語意檢索 | 0.83 | 0.88 | 0.86 |
| 純詞彙檢索 | 0.33 | 0.54 | 0.44 |
| 混合檢索 | 0.58 | 0.79 | 0.70 |
| 混合＋識別碼釘選（原本的設計） | 0.58 | 0.83 | 0.71 |
| **語意＋識別碼釘選（現行）** | **0.83** | **0.92** | **0.87** |
| 詞彙＋識別碼釘選（無金鑰備援） | 0.38 | 0.63 | 0.49 |

原本假設混合檢索最好。實測發現字元比對在中文換句話說的題目幾乎全數失敗（6 題只中 1 題），
而等權合併讓弱的一路把正確答案往後推，因此改為語意檢索＋識別碼釘選。
題目由作者撰寫、題數少，僅適合比較不同設計的相對強弱。

## 快速開始

```bash
pip install -r requirements.txt
python src/generate_data.py        # 合成資料與 52 封模擬信件（含 10 封手寫刁鑽案例）
python src/build_erp_db.py         # 模擬 ERP 資料庫 data/erp_sim.db
python src/generate_history.py     # 1494 張歷史單與收貨紀錄
python -m pytest tests -q          # 266 項測試，全部離線
python -m streamlit run app.py     # 啟動介面
```

Windows 若 `python` 不在 PATH，改用 `py -X utf8`。

**接上 LLM（選用）**：複製 `.env.example` 為 `.env` 並填入金鑰。
沒有金鑰時工具仍可完整執行並明確標示：口語敘述信件標記為需人工確認、檢索改用詞彙比對、回信草稿改用模板。

**重新產生評估報告**：

```bash
python src/evaluate.py             # 解析：規則層 vs LLM 層（需金鑰）
python src/rag/evaluate_rag.py     # 檢索：六種配置（需金鑰）
python src/backtest.py             # 回測（不需金鑰）
```

## 部署

部署到 Streamlit Community Cloud 的步驟見 [`docs/部署指引.md`](docs/部署指引.md)。

公開展示時的保護設計：
- **種子快取**（`demo_cache/`）：解析結果、知識卡向量與範例問答預先算好一併部署，
  冷啟動不必呼叫 API。已在封鎖網路的乾淨副本上驗證呼叫次數為 0
- **工作階段額度**：每位訪客最多觸發 20 次未快取的 LLM 呼叫（`LLM_CALLS_PER_SESSION`），
  用完後工具仍可使用，只是改為列出原始資料或使用模板

## 已知限制

| 項目 | 現況 |
|---|---|
| 交期預測 | 沒有預測模型。保守到料日是歷史統計，不知道「這一張單」會怎樣 |
| 回測結果 | 與「只看供應商說的日期」打平；P95 涵蓋率 90%，低於預期 |
| 百分位與收貨處理天數 | 都是領域假設；收貨處理天數查不到公開依據，依到廠作業步驟推得 |
| 歷史單不分批 | 歷史刻意維持單一排程行，回測與落差估計沒有分批交貨的情境 |
| 收貨紀錄對排程行 | `goods_receipt` 以「採購單＋項次」為鍵，分批交貨的兩批共用同一個收貨判斷 |
| 需求日 | 視為 MRP 淨需求日（已扣庫存與在途）；若接的是毛需求，缺料天數會高估 |
| 月度績效 | 逾期未收的單，延遲天數只算到基準日，是低估值 |
| 雲端展示的設定 | 企劃的調整與確認在 App 休眠或重新部署後會消失 |
| 封測段、載板段 | 沒有專屬規則（作者實務經驗在晶圓廠） |
| 價格與商務條款 | 完全未處理 |
| 真實 ERP 串接 | 已定義資料介面與欄位對應，未接過生產環境 |
| 信件來源 | 讀取本機檔案；實務應接郵件伺服器 |
| 模型相對日期推算 | 跨年會算錯年份、「下個月」會算成本月；由「需人工確認」攔截，改由程式計算列為下一步 |
| 檢索評估 | 題目由作者撰寫、題數少，僅供比較設計 |
| 快取期限 | 無失效期限，資料更新後需重新產生 |

## 導入真實環境的下一步

1. **先訪談再寫程式**：觀察物料企劃實際處理一封回覆信的流程，P1／P2／P3 的條件有幾條會被推翻
2. **影子運行兩到四週**：工具只跑不給人看，比對它的清單與企劃實際追料的順序
3. **從一位窗口、一類料開始**，讓使用者隨時可以關掉工具
4. **收集企劃的確認與調整紀錄**：誰在什麼時候把模糊的日期變成承諾、哪些料號的收貨處理天數被改過、為什麼 ——
   這是 ERP 結構上不會有的資料，也是回頭修正料號主檔與百分位的依據
5. **用真實收貨紀錄重跑回測**：確認保守到料日的涵蓋率，以及排序是否贏過「只看供應商說的日期」
