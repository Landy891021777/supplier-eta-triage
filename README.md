# Supply Chain AI Tool: Delivery Risk Prioritization

**供應鏈 AI 工具：交期風險優先排序**

生管每天收到大量供應商交期回覆信：格式各異、中英夾雜、措辭模糊。
這個工具讀懂這些信、對回採購單、依領域規則排出今天該先追哪幾張，
並讓生管在同一個畫面看到**這家供應商過去說話算不算數**。

> ⚠️ **誠實聲明**：本專案全部使用**合成資料**，未使用任何公司的真實資料，也未串接真實 ERP。
> 真實的採購單與交期屬營業秘密，因此以程式產生資料，並把領域假設寫成可逐條檢視的程式碼
> （見 `src/generate_data.py` 的 `# 領域假設：` 註解）。
> 合成資料上的所有數字只能證明程式邏輯自洽，不能證明真實環境有效。

## 功能一覽

| 模組 | 做什麼 | 關鍵設計 |
|---|---|---|
| **① 讀信** | 把供應商回覆信轉成結構化的交期變更 | 規則優先，語意模糊才交給 LLM；判讀供應商「到底有沒有承諾」 |
| **② 排序** | 排出生管今天該先追的採購單 | 十條可調權重的領域規則，每筆附理由；不確定的交期不寫回系統 |
| **③ ERP 與歷史** | 以模擬 ERP 算出供應商實際準交表現 | SQLite 資料表結構參考 SAP MM；歷史實績同時用來輔助判斷與驗證規則 |
| **④ 物料智能檢索** | 用自然語言查採購單、料號、供應商與工具說明 | 語意檢索＋識別碼精確比對；每個事實標出處，並驗證出處真實存在 |

```
供應商回覆信
    │
    ▼
① 讀信   規則層（免費、可重現）──信心不足──► LLM 層
    │      同時判讀承諾強度：已確認／暫估／僅表達意向
    ▼
② 排序   對回採購單 → 十條規則評分 → 今日追蹤清單
    │      非「已確認」的交期：標記人工確認，不寫回系統
    ▼
③ 歷史   模擬 ERP（10 張表）→ 供應商準交率、保守到料日
    │      ──► 同一批實績回頭驗證排序規則
    ▼
④ 檢索   「PO-2026-04205 的供應商可靠嗎？」→ 附出處的回答
```

## ① 讀信：規則優先，模糊才交給 LLM

一天幾百封信全部送 LLM，成本、延遲都讓人不想用，結果也無法重現。
所以先用程式規則解析（四種日期格式、欄位標籤、表格同列比對、「照原計畫」等反向語意），
**規則層判斷自己沒把握時才升級呼叫 LLM**：相對日期、轉寄串、一封多單、含模糊措辭。

**承諾強度是這一層最重要的欄位。**
供應商寫「大概月底吧，我再跟你確認」—— 若工具把它抽成 `2026-10-31` 填進表格，
生管會以為事情定了。所以解析時必須同時判斷這句話算不算承諾：

| 判定 | 例句 | 工具的處理 |
|---|---|---|
| 已確認 | 「Revised ETA 10/30, confirmed」 | 可作為排程依據 |
| 暫估 | 「around Oct 20 but not yet locked」 | 標記人工確認 |
| 僅表達意向 | 「我們盡量」「cannot commit a firm date」 | 標記人工確認，**不可**作為排程依據 |

LLM 的 prompt 會帶入系統裡的原承諾日。供應商寫「往後兩週」時，信裡並沒有原本是哪天 ——
那個資訊在我方系統，不給模型就是要它猜。

## ② 排序：十條規則，每筆說得出理由

| 規則 | 預設權重 | 判斷什麼 |
|---|---:|---|
| 緩衝天數 | 25 | 新交期距下游需求日還剩幾天 |
| 下游已排定 | 15 | 產能是否已排、是否已對客戶承諾 |
| 單一來源 | 12 | 有無已認證的第二家供應商 |
| 延遲幅度 | 10 | 比原承諾晚幾天 |
| 承諾強度 | 10 | 越不確定越該優先追 |
| 料的關鍵性 | 8 | 瓶頸料、長前置期料 |
| 累犯 | 6 | 這張單已改期幾次 |
| 延遲量佔比 | 6 | 佔當期需求多少 |
| 通知時機 | 5 | 距原承諾日剩幾天才通知 |
| 可替代性 | 3 | 有無替代料 |

權重是相對份量，在介面上可即時調整並立刻重排。
**說不出理由的排序，同仁用兩週就會棄用**，所以每一筆都能展開看到十條規則各拿幾分。

## ③ ERP 與歷史：供應商說的話能信幾分

以 SQLite 建立 10 張資料表，結構參考 SAP MM 的公開資料整理（非任何公司實際結構）：

```
vendor_master (≈LFA1)    material_master (≈MARA/MARC)   material_alternate
source_list (≈EORD)      purchase_req (≈EBAN)           po_header (≈EKKO)
po_item (≈EKPO)          po_schedule (≈EKET)            po_change_log (≈CDHDR/CDPOS)
goods_receipt (≈MKPF/MSEG)
```

工具需要的判斷依據，**有好幾項在 ERP 裡沒有現成欄位**，必須用 SQL 推導：
承諾日在交貨排程行、需求日在請購單、改期次數要數變更文件、有無二源要數來源清單的合格供應商。

歷史收貨紀錄有兩個用途：

**給生管當下判斷**：行動清單每一筆旁顯示該供應商的歷史準交率，
以及依其歷史延遲分布推算的保守到料日。樣本不足的供應商不給估計。

**回頭驗證規則**：例如「累犯」這條規則是否成立 ——

| 改期情形 | 樣本數 | 最終仍延遲比例 |
|---|---:|---:|
| 未改期 | 504 | 28.4% |
| 改期 1 次 | 209 | 37.3% |
| 改期 2 次 | 95 | 38.9% |
| 改期 3 次以上 | 90 | 53.3% |

## ④ 物料智能檢索（RAG）

用平常講話的方式查詢，例如「哪些料缺了沒辦法找別家救？」「PO-2026-04205 的供應商可靠嗎？」

**切塊**：結構化資料一個實體一張卡（一張採購單被切兩半就沒用了）；文件依標題切並補上出處。
另建**摘要卡**處理排名類問題 —— 檢索只會撈出幾張相似的卡，做不了「12 家裡誰最差」這種比較。

**檢索**：語意檢索＋識別碼精確比對。問題裡出現單號、料號時直接取出，
並沿關聯多取一層（採購單 → 它的料號與供應商），因為答案常常不在被點名的那張卡上。

**回答**：只能根據檢索到的資料回答，每個事實標出處。
程式另外**驗證模型引用的出處是否真的有給它** —— 開發時第一次試跑就抓到模型引用了沒撈到的卡片。
資料裡沒有的（例如真實公司名稱），會直接回答沒有。

## 評估：每個設計決定都要有證據

三組評估的完整結果在 `output/`，介面「🧪 評估實驗」分頁可直接查看。

### 解析：這裡到底需不需要 LLM？

52 封人工標註答案的信件，依書寫風格分群，規則層與 LLM 層各跑一次（`src/evaluate.py`）：

| 信件風格 | 封數 | 日期正確（規則→LLM） | 承諾強度正確（規則→LLM） |
|---|---:|---|---|
| 格式化通知 | 16 | 1.00 → 1.00 | 1.00 → 1.00 |
| 半格式化 | 10 | 1.00 → 1.00 | 1.00 → 1.00 |
| 確認不變 | 5 | — | 1.00 → 1.00 |
| 口語敘述 | 11 | **0.00 → 1.00** | 0.36 → 0.64 |
| 手寫刁鑽案例 | 10 | **0.33 → 0.89** | **0.48 → 1.00** |

格式化信件規則層已經全對，**不該送 LLM**；口語敘述與刁鑽案例規則層失效，才是 LLM 的存在理由。
（信件的風格比例是資料產生器設定的，因此不宣稱「幾成信件不需 LLM」這種比例。）

### 檢索：評估推翻了原本的設計

24 題、六種配置（`src/rag/evaluate_rag.py`）：

| 配置 | Hit@1 | Hit@3 | MRR |
|---|---:|---:|---:|
| 純語意檢索 | 0.79 | 0.92 | 0.85 |
| 純詞彙檢索 | 0.29 | 0.50 | 0.39 |
| 混合檢索 | 0.50 | 0.79 | 0.67 |
| 混合＋識別碼釘選（原本的設計） | 0.54 | 0.83 | 0.70 |
| **語意＋識別碼釘選（現行）** | **0.79** | **0.96** | **0.87** |
| 詞彙＋識別碼釘選（無金鑰備援） | 0.38 | 0.58 | 0.47 |

原本假設混合檢索最好。實測發現字元比對在中文換句話說的題目全數失敗，
而等權合併讓弱的一路把正確答案往後推，因此改為語意檢索＋識別碼釘選。
題目由作者撰寫、題數少，僅適合比較不同設計的相對強弱。

### 權重校準：資料同不同意我訂的權重

以 394 筆曾收到改期通知的已結案單（85 筆實際缺料）做邏輯迴歸（`src/calibrate.py`）：

- 資料認為**料的關鍵性、單一來源、累犯**比我設定的更重要
- 學習模型 AUC 0.79，人訂評分卡 0.71。歷史結果由我寫的因果規則產生，模型贏是意料之中，
  **不構成換掉評分卡的證據**，需以真實資料再驗證
- 「下游已排定」等三條被判方向相反，但**不該拿掉**：校準的結果是「會不會缺料」，
  而這三條衡量的是「缺了有多痛」。評分卡同時在衡量機率與代價，歷史資料只能校準前者

**承諾強度無法校準** —— ERP 只存結果、不存語氣。這正是這個工具產生、而 ERP 結構上不會有的資料。

## 快速開始

```bash
pip install -r requirements.txt
python src/generate_data.py        # 合成資料與模擬信件
python src/build_erp_db.py         # 模擬 ERP 資料庫
python src/generate_history.py     # 歷史單據與收貨紀錄
python -m pytest tests -q          # 81 項測試
python -m streamlit run app.py     # 啟動介面
```

Windows 若 `python` 不在 PATH，改用 `py -X utf8`。

**接上 LLM（選用）**：複製 `.env.example` 為 `.env` 並填入金鑰。
沒有金鑰時工具仍可完整執行：口語敘述信件標記為需人工確認、檢索改用詞彙比對、回信草稿改用模板。

**重新產生評估報告**（需要金鑰）：

```bash
python src/evaluate.py             # 解析：規則層 vs LLM 層
python src/rag/evaluate_rag.py     # 檢索：六種配置
python src/calibrate.py            # 權重校準
```

## 部署

部署到 Streamlit Community Cloud 的步驟見 [`docs/部署指引.md`](docs/部署指引.md)。

公開展示時的保護設計：
- **種子快取**（`demo_cache/`）：解析結果、知識卡向量與範例問答預先算好一併部署，
  冷啟動不必呼叫 API。已在封鎖網路的乾淨副本上驗證呼叫次數為 0
- **工作階段額度**：每位訪客最多觸發 20 次未快取的 LLM 呼叫（`LLM_CALLS_PER_SESSION`），
  用完後工具仍可使用，只是改為列出原始資料或使用模板

## 已知限制

| 項目 | 現況 |
|---|---|
| 分批交貨 | 只取最晚一批；正確做法需將每筆排程行分開追蹤 |
| 封測段、載板段 | 只有欄位，未實作專屬規則（作者實務經驗在晶圓段） |
| 價格與商務條款 | 完全未處理 |
| 真實 ERP 串接 | 已定義資料介面與欄位對應，未接過生產環境 |
| 信件來源 | 讀取本機檔案；實務應接郵件伺服器 |
| 模型相對日期推算 | 已知會算錯月份，由人工確認閘門攔截 |
| 檢索評估 | 24 題、作者自行撰寫，僅供比較設計 |
| 快取期限 | 無失效期限，資料更新後需重新產生 |

## 導入真實環境的下一步

1. **先訪談再寫程式**：觀察生管實際處理一封回覆信的流程，十條規則有幾條會被推翻
2. **影子運行兩到四週**：工具只跑不給人看，比對它的排序與同仁實際處理順序
3. **從一位窗口、一類料開始**，讓使用者隨時可以關掉工具
4. **收集權重調整與理由**：同仁調了哪一條、為什麼，就是要回寫進設定檔的領域知識
5. **累積真實結果後再談模型**：這張評分卡就是模型必須贏過的基準
