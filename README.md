# 供應商交期回覆解析與影響評估工具

> 把供應商散落在信件裡的交期回覆，自動解析、對位到採購單、依領域規則判斷影響，
> 收斂成生管今天真正該處理的優先清單。
>
> **核心論述：抽取交給 LLM，判斷交給領域規則。**
> 前者是通用能力，後者是供應鏈專業。

---

## ⚠️ 誠實聲明（請先讀這段）

**本專案使用的是合成資料，不是任何公司的真實資料。**

真實的採購單、交期與供應商往來屬營業秘密，不可能出現在公開作品集裡。
但「因為沒資料所以隨便亂灑」是不負責任的做法，因此本專案的作法是：

> **把領域假設外顯化，寫成任何人都能逐條檢視、質疑、修改的程式碼。**

資料產生器 [`src/generate_data.py`](src/generate_data.py) 裡每一段
`# 領域假設：` 註解，都是我在晶圓廠做物料企劃時的實際觀察。
它們可能不完全適用於每一家公司 —— **那正是我希望被挑戰的地方。**

因此請把資料產生器與 [`src/impact.py`](src/impact.py) 的十條規則
當成本專案的主要交付物來讀，而不是把重點放在任何指標數字上。

**評估上的限制**：在合成資料上得到的任何數字，只能證明程式邏輯自洽，
不能證明在真實環境有效。真實效能必須上線後以 A/B 驗證。
本文件中所有數字都附有計算方式與假設，請連同假設一起引用。

**視角說明**：作者的實務背景在晶圓廠物料企劃（供應商端）。
本專案以 fabless 情境（向 foundry／封測／載板廠委外）為問題設定，
但 fabless 內部流程細節（die bank 投料政策、產能 allocation、長約與 NRE 等）
是依公開產業知識推論，未經實務驗證，實際導入需與生管、採購同仁確認。
專案範圍刻意鎖定 **wafer 段**，因為那是作者特徵判斷最有把握的環節。

## 一、要解決什麼問題

生管與採購每天會收到大量供應商的交期回覆信。這些信有幾個特性：

| 特性 | 造成的麻煩 |
|---|---|
| 格式各異 | 有表格、有純敘述、有轉寄串 |
| 中英夾雜 | 同一封信裡「Revised ETA」和「大概月底」並存 |
| 措辭模糊 | 「往後抓個兩週，我再跟你確認」到底算不算承諾？ |
| 一封多單 | 一封信講三張採購單，一張延、一張不變、一張提前 |
| 資訊不完整 | 「push out to next quarter」根本沒有可用日期 |

現況的處理方式是：**人工逐封讀 → 開 ERP 查原承諾日 → 心算緩衝夠不夠
→ 憑經驗決定先追哪一張。** 這件事每天要做一次，而且做得好不好完全靠個人經驗。

更麻煩的是：**信件本身不會告訴你這件事痛不痛。**
延 30 天但下游還沒排的單，遠不如延 3 天卻卡住已排定產能的單來得急。
要判斷這件事，必須把信件內容跟採購單、料號、供應商的狀態合起來看。

## 二、工具做什麼

```
資料層     供應商主檔 / 採購單主檔 / 料號主檔 / 供應商回覆信件
             │
第 1 層     規則解析器（免費、毫秒級、結果可重現）
             │  輸出信心分數
             ▼  信心不足才升級  ─────────────────────┐
第 2 層     LLM 解析                                  │ 無金鑰時
             │  額外抽取「承諾強度」                   │ 自動降級
             │  確認 / 暫估 / 僅表達意向               │ 退回規則層
             ▼ ◄──────────────────────────────────────┘
第 3 層     對位採購單主檔 → 判定延遲／提前／無變更 → 算出與原承諾的差異
             │
第 4 層     十條影響規則（權重可即時調整）→ 優先序清單
             │
輸出        行動清單 ＋ 逐條理由 ＋ 回信草稿 ＋ 人工確認閘門
```

### 一次執行的實際結果（合成資料，52 封信，已接 Gemini）

| 項目 | 數量 |
|---|---|
| 收到的信件 | 52 |
| 解析出的變更筆數 | 56 |
| 自動濾除（供應商確認無變更） | 8 |
| 進入行動清單 | 47 |
| 🔴 今天要處理（P1） | 9 |
| 🟠 本週要追（P2） | 22 |
| ⚠️ 標記為需人工確認 | 14 |
| **規則層即可處理、未呼叫 LLM** | **27 / 52** |
| 升級至 LLM 且呼叫成功 | 25 / 25 |

## 三、三個核心設計決定

### 1. 分層解析 —— 能用規則解決的，就不要花 token

一天幾百封信全部丟給 LLM，成本與延遲都會讓同仁不想用，IT 也會有意見。
所以先跑免費的規則層，只有信心低於門檻（預設 0.75）的才升級。

這不只是省錢。**規則層的結果是完全可重現的** ——
同一封格式化通知信，每次跑都得到一樣的答案，稽核起來容易得多。

門檻寫在 `config.yaml`，調高則更多信走 LLM（準度高、成本高），
調低則省成本但漏抽風險上升。這個取捨應該由使用單位決定，不是開發者決定。

### 2. 承諾強度 —— AI 工具最大的風險不是答錯，是把不確定的事講得很確定

供應商回信說「大概月底吧，我再跟你確認」。

如果工具把它抽成 `2026-10-31` 填進表格，生管看到一個確切日期，
就會以為事情定了，然後拿去排下游產能。
**把不確定性洗掉，比不解析還危險。**

所以解析層除了日期，還必須判斷「這句話到底算不算承諾」：

| 承諾強度 | 判準 | 工具的處理 |
|---|---|---|
| `confirmed` | 明確承諾、或已在對方系統鎖定 | 可作為排程依據 |
| `estimated` | 給了日期但帶保留語氣 | 標記需人工確認 |
| `intent_only` | 僅表達意圖、明講無法承諾 | 標記需人工確認，且**不可**作為排程依據 |

規則：**只要出現任何退路措辭，就不可以填 `confirmed`。**
寧可多追一次，不可少追一次。

### 3. 人工確認閘門 —— 工具永遠不自動寫回 ERP

非 `confirmed` 的解析結果、信心不足的結果、以及「有延遲但沒有可用日期」的結果，
一律標記為需人工確認，且不覆寫系統承諾日。

理由很簡單：**交期資料錯了，下游整條排程都會跟著錯。**
這個代價不能由工具自動承擔。工具的責任是把「查資料 + 判斷 + 打字」這段省掉，
決定權留給人。同理，回信一律只產生草稿，工具不會替使用者寄出任何信件。

## 四、這裡到底需不需要 LLM？（對照實驗）

很多 AI 專案跳過這一步，直接假設「用了 AI 就比較好」。
本專案認為那是不負責任的：LLM 有成本、有延遲、有不可重現性，
**導入它必須先證明規則做不到。**

作法：對同一批信件、同一份人工標註答案，分別用兩層解析，依書寫風格分群比較。
執行 `py src/evaluate.py` 可重現，結果輸出到 `output/實驗結果.md`。

### 兩層對照結果（實際執行，模型：`gemini-3.5-flash-lite`）

| 信件風格 | 封數 | 日期正確（規則→LLM） | 承諾強度正確（規則→LLM） | 變更類型正確（規則→LLM） |
|---|---:|---|---|---|
| formal（格式化通知） | 16 | **1.000 → 1.000** | 1.000 → 1.000 | 1.000 → 1.000 |
| semi（半格式化） | 10 | **1.000 → 1.000** | 1.000 → 1.000 | 1.000 → 1.000 |
| no_change（確認不變） | 5 | — | 1.000 → 1.000 | 1.000 → 1.000 |
| **narrative（純敘述）** | 11 | **0.000 → 1.000** | 0.364 → 0.636 | **0.000 → 1.000** |
| **handcrafted（刁鑽案例）** | 10 | **0.333 → 0.889** | 0.483 → **1.000** | 0.483 → 0.900 |

（PO 號命中率兩層皆為 1.000，故未列入表格。）

### 結論：分層是對的

**上半部三群（31 封，佔 60%）：兩層完全相同，全部滿分。**
這些信**不該**送 LLM —— 規則層已經全對，送出去只是浪費錢、增加延遲，
而且失去可重現性。這一組數據是「不要用 AI」的證據，我把它列在最前面。

**下半部兩群（21 封，佔 40%）：規則層崩潰，LLM 大幅勝出。**
日期正確率 0.000 → 1.000、0.333 → 0.889；承諾強度 0.483 → 1.000。
失效原因是相對日期（「往後兩週」）、模糊措辭（「大概月底」）、
轉寄串裡的舊日期、一封多單且結論不同。**這才是導入 LLM 的實質理由。**

規則層是認真寫的，不是為了襯托 LLM 的稻草人 —— 它涵蓋四種日期格式、
欄位標籤角色判讀、同列表格解析、反向語意偵測。正因為它是認真寫的，
它在上半部的滿分才有說服力，它在下半部的失敗才構成證據。

> 這個實驗必須容許得出「不要用 LLM」的結論，否則它不是實驗，是背書。
> 而它確實對 60% 的信件得出了這個結論。

### 這個實驗踩過的兩個坑（保留紀錄，因為它們比結果更有教育意義）

**坑一：把配額限制誤讀成模型能力。**
第一次執行時 LLM 欄位大面積掛零，看起來像是「模型解析不出來」。
實際原因是 HTTP 429 —— 免費層速率限制。若當時就下結論，
會得到完全相反且錯誤的技術判斷。
修正方式是加入節流、退避重試與結果快取（見 `src/llm/provider.py`），
之後 LLM 呼叫成功率從約 40% 變成 25/25。

**坑二：標準答案不可從文字還原。**
narrative 群一度兩層都是 0.000。原因是信裡寫「往後抓個兩週」，
但標準答案存的是精確天數 —— **那道題沒有答案，任何模型都會零分。**
而且信裡沒寫原承諾日，模型也無從推算絕對日期。

修正包含兩部分：(a) 讓標準答案由信件文字實際決定；
(b) **把系統已知的原承諾日帶進 prompt** —— 信件提供「變化」，
系統提供「基準」，這本來就是正確的架構。修正後該群從 0.000 變成 1.000。

> 評估資料的瑕疵會產生錯誤的技術結論，而錯誤的技術結論會導致錯誤的架構決定。
> 這兩個坑我保留在 commit 歷史與程式註解裡，沒有清掉。

## 五、效益量化

**這裡不會出現「節省 30% 人力」這種數字。** 那種數字沒有根據，
被追問一句「怎麼算的」就會垮掉。以下提供的是**公式 + 可調參數 + 敏感度分析**。

### 1. 訊息壓縮（無假設，程式直接計算）

```
52 封信  →  56 筆變更  →  濾除 8 筆「供應商確認無變更」
         →  47 件行動項  →  31 件需今天或本週處理（P1+P2）
```

生管實際要細看的項目從 **52 降到 31**。這個數字沒有任何假設參數。

### 2. 排序品質：Recall@20

若生管一天只能仔細追 20 件，各種排序方式各能抓到多少比例的
「真的會來不及」案件？（會不會來不及 = 新交期是否晚於下游需求日，
由兩個日期相減得到，**不是模型輸出**。本批 47 件中有 25 件會來不及。）

| 策略 | Recall@20 |
|---|---:|
| **本工具（影響分數排序）** | **0.760** |
| 土法：依延遲天數排序 | 0.640 |
| 隨機抽查（200 次平均） | 0.428 |
| 現況：依收信時間 (FCFS) | 0.400 |

**必須誠實指出三件事：**

**（a）領先幅度是溫和的，不是壓倒性的。**
0.760 對 0.640，換算成實際案件是「多抓到 3 件」（19 件 vs 16 件，共 25 件）。
一個懂行的生管用土法排序也能排得不錯。**排序本身不是這個工具的主要價值。**

**（b）工具真正的價值在前面那一段。**
土法排序的前提是「已經有人把 52 封信讀完、查過 ERP、把日期 key 好了」。
本工具取代的正是那一段人工作業，以及土法完全做不到的兩件事：
標記出**哪些日期不可信**（承諾強度），以及**哪些案子系統看不懂、需要人介入**。

**（c）這個比較對本工具有利。** 影響分數的規則 1（緩衝天數，權重 25）
使用了與 outcome 相同的訊號。它證明的是排序邏輯有效地把緩衝訊號傳遞到清單前段，
**不能**證明工具可以預測未知結果。

### 3. 工時敏感度分析

不給單一數字，給一張表 —— 因為「人工判讀一封信要幾分鐘」每家公司都不一樣。
請挑你認同的那一列來看。（工具端假設每件行動項 45 秒；每月 21 個工作日）

| 假設：人工判讀一封信 | 現況每日工時 | 用工具後每日工時 | 每日節省 | 每月節省 |
|---:|---:|---:|---:|---:|
| 90 秒 | 1.30 | 0.39 | 0.91 | 19.2 小時 |
| 120 秒 | 1.73 | 0.39 | 1.35 | 28.3 小時 |
| 180 秒 | 2.60 | 0.39 | 2.21 | 46.5 小時 |
| 240 秒 | 3.47 | 0.39 | 3.08 | 64.7 小時 |
| 300 秒 | 4.33 | 0.39 | 3.95 | 82.9 小時 |

參數全部寫在 `config.yaml`，可依實際單位調整後重新計算。

### 4. 一個模型答錯、但被閘門攔下來的實例

手寫案例 HC-005 的信件寫著：

> 「I cannot commit a firm date at this moment, but 我們盡量在下個月中之前出貨。」

正確答案是 `2026-10-15`。**模型算成 `2026-09-15`（月份少算一個月）**，
因而讓系統誤判成「提前交貨」。

但這筆的承諾強度被正確判成 `intent_only`，因此觸發人工確認閘門 ——
**它不會覆寫系統承諾日，且在清單上標著 ⚠️ 要求生管自己看一眼原信。**

這正是那道閘門存在的理由：**模型一定會出錯，設計的責任是讓它出錯時
不會造成下游損害。** 這個案例保留在專案裡，沒有為了讓數字好看而拿掉。

## 六、十條影響規則

完整實作與逐條說明見 [`src/impact.py`](src/impact.py)。
每條規則獨立產生 0~1 分數與一句給生管看的理由，加權平均後得到影響分數。

| # | 規則 | 預設權重 | 為什麼 |
|---:|---|---:|---|
| 1 | 緩衝天數 | 25 | 延遲本身不痛，**來不來得及**才痛。第一順位。 |
| 2 | 延遲幅度 | 10 | 權重刻意壓低 —— 照延遲天數排序是常見的錯。 |
| 3 | 單一來源 | 12 | 有二源是商務問題，沒二源是無解問題。 |
| 4 | 下游已排定 | 15 | 已排產能或已對客戶承諾 → 代價放大。 |
| 5 | 料的關鍵性 | 8 | 瓶頸料與長前置期料補不回來。 |
| 6 | **承諾強度** | 10 | 越不確定越該處理（方向反直覺但正確）。 |
| 7 | 累犯 | 6 | 第三次改期的供應商，這次也不能信。 |
| 8 | 延遲量佔比 | 6 | 延 10% 可吸收，延 90% 是斷料。 |
| 9 | 通知時機 | 5 | 提早三週講還有救，前一天講是災難。 |
| 10 | 可替代性 | 3 | 要跑工程變更，緩不濟急，是最後一張牌。 |

**權重全部寫在 `config.yaml`，且在介面上可即時調整。**
這是刻意的設計：內部工具的第一版一定會被質疑「你憑什麼這樣排」。
把權重外部化，同仁才能參與調校，工具才活得下去。
說不出理由的黑箱，同仁用兩週就會棄用。

## 七、快速開始

```bash
pip install -r requirements.txt
python src/generate_data.py      # 產生合成資料與模擬信件
python src/evaluate.py           # 執行規則層 vs LLM 對照實驗
python -m pytest tests -q        # 執行測試（35 項）
python -m streamlit run app.py   # 啟動介面
```

Windows 上若 `python` / `streamlit` 不在 PATH，改用：

```bash
py -X utf8 -m streamlit run app.py
```

**接上 LLM（可選）**：複製 `.env.example` 為 `.env`，填入金鑰。
`.env` 已被 `.gitignore` 排除，不會進版控。
免費金鑰可在 Google AI Studio 取得。**沒有金鑰時工具仍可完整執行**，
只是自然語言敘述型的信件會解析失敗並標記為需人工確認 —— 這是預期的降級行為。

關於配額：免費層有速率與每日上限，且模型名稱會汰換
（本專案開發期間 `gemini-2.0-flash` 已下線、`gemini-3.6-flash` 每日僅 20 次）。
因此 provider 內建**節流、退避重試與結果快取**：

| 環境變數 | 預設 | 用途 |
|---|---|---|
| `LLM_MIN_INTERVAL_S` | `4.0` | 兩次呼叫的最小間隔，避免整批被打成 429 |
| `LLM_MAX_RETRIES` | `3` | 遇到 429/5xx 時的退避重試次數（尊重服務商回傳的 `retryDelay`） |
| `LLM_CACHE` | `1` | 以 provider+模型+prompt 雜湊為鍵的本機快取，設 `0` 關閉 |

快取讓反覆執行實驗不會重複燒配額，也讓結果在 prompt 未變時保持一致。

## 九、已知限制與未實作項目

誠實列出，因為知道自己沒做什麼，跟知道自己做了什麼一樣重要。

| 項目 | 現況 | 為什麼 |
|---|---|---|
| **分批交貨** | 只取最晚的一批當新交期 | 實務上很常見，但正確處理需要拆分採購單行項目，涉及 ERP 資料結構 |
| **封測段 / 載板段專屬規則** | 只有欄位，未實作規則 | 作者實務在 wafer 段，那兩段的判斷沒有把握，不硬寫 |
| **價格與商務條款** | 完全未處理 | 作者是物料企劃不是採購，階梯價、NRE、長約、匯率沒有實務基礎 |
| **真實 ERP 串接** | 未實作 | 需要實際的 SAP/ERP 環境與權限 |
| **信件來源** | 讀取本機文字檔 | 實務上應接 Exchange/Graph API 或 IMAP |
| **供應商評鑑累積** | 未實作 | 規則 9 的通知時機資料長期累積後可作為評鑑依據，值得做但不在本版 |
| **LLM 輸出的一致性** | 未做多次取樣驗證 | 生產環境應加上 self-consistency 或雙模型交叉驗證 |
| **成本監控** | 只有節流與快取，無用量儀表板 | 生產環境需要 token 用量統計與預算告警 |
| **模型會算錯相對日期** | 已知會發生（見效益章節第 4 點） | 靠人工確認閘門攔截，而非假設模型不會錯 |
| **快取無失效期限** | 永久有效，直到 prompt 改變 | 生產環境應加上 TTL，否則資料更新後仍讀到舊解析 |

## 十、若要導入真實環境，下一步

1. **先訪談，不要先寫程式。**
   找三位生管、兩位採購，看他們實際怎麼處理一封交期回覆信，
   計時、記錄卡在哪裡。十條規則有幾條會被推翻，這是好事。
2. **先影子運行（shadow mode）。**
   工具跑但不給任何人看，每天把它的排序跟同仁實際處理順序做比對，
   累積兩到四週。這期間收集到的「預警 vs 實際結果」，
   才是未來訓練機器學習模型的第一份真實資料。
3. **從一個窗口、一類料開始。**
   不要一次上線給整個部門。找一位願意當白老鼠的同仁，
   讓他有權隨時關掉工具改用原本的方法。
4. **權重交給使用者調。**
   上線第一個月最重要的產出不是準確率，是**同仁調了哪些權重、為什麼調**。
   那些調整就是領域知識，應該回寫進 `config.yaml` 並記錄理由。
5. **等有真實資料了，再談模型。**
   累積三到六個月的預警與實際結果之後，這張評分卡就是模型的 baseline。
   **沒有 baseline 的模型沒有意義** —— 你無法證明它比規則好。
