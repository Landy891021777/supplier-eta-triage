# ERP 欄位對應與整合設計

> **誠實聲明**：我沒有實際串接過生產環境的 ERP。
> 本文的表名與結構是參考 SAP ECC/S4 的公開資料整理的近似版本，
> 各家公司的客製化程度差異很大，實際導入必須與 IT 逐欄確認。
>
> 這份文件的用途是**把整合的介面定義清楚**，讓「接上去」變成一件
> 範圍明確、可估時的工作，而不是一句「之後可以串 ERP」的空話。

---

## 一、為什麼不是「把 ERP 的表撈出來就好」

工具需要的十個判斷輸入，**有五個在 ERP 裡不存在現成欄位**，必須推導：

| 工具需要的 | ERP 裡的實際樣子 | 要做的事 |
|---|---|---|
| 供應商承諾日 | 不在採購單頭，在**交貨排程行** | 一個項次可能有多筆排程行（分批交貨），要決定取哪一筆 |
| 下游需求日 | 不在採購單，在**請購單**或 MRP 需求 | JOIN 請購單 |
| 已改期幾次 | **沒有這一欄**，藏在變更文件 | COUNT 承諾日被修改的筆數 |
| 有無已認證二源 | **不是布林欄位**，在來源清單 | 數該料號的合格供應商家數 |
| 本單佔當期需求比例 | **沒有這一欄** | 本單量 ÷ 請購單當期需求量 |

**把這些欄位直接寫成一張扁平表，等於跳過了整合工作中最花時間的部分。**
因此本專案建了一個結構貼近 ERP 的模擬資料庫（`src/build_erp_db.py`），
強迫自己用真正的 SQL 面對這件事。

---

## 二、資料表對應

| 模擬資料庫 | SAP（舉例） | 用途 |
|---|---|---|
| `vendor_master` | LFA1 | 供應商主檔 |
| `material_master` | MARA / MARC | 料號主檔、標準前置期 |
| `material_master.base_uom` | MARA-MEINS | 基本計量單位 |
| `material_master.gr_processing_days` | MARC-WEBAZ | 收貨處理時間：到廠後幾天才能投產（MRP 算可用日時會加上這天數） |
| `material_alternate` | BOM 替代群組 / 主檔替代關係 | 替代料 |
| `source_list` | EORD | **來源清單 —— 二源判定的權威來源** |
| `purchase_req` | EBAN | **請購單 —— 需求日的來源** |
| `po_header` | EKKO | 採購單頭 |
| `po_item` | EKPO | 採購單項次 |
| `po_schedule` | EKET | **交貨排程行 —— 承諾日的來源** |
| `po_change_log` | CDHDR / CDPOS | **變更文件 —— 改期次數的來源** |
| `goods_receipt` | MKPF / MSEG | 收貨紀錄 —— 未來校準權重的 outcome |

另外值得注意但本版未使用的：

- **EKES（訂單確認 / AB）** — 供應商回覆的確認日期會落在這裡。
  真實導入時，工具解析出的日期應該與這張表比對，找出「信裡講的」
  和「系統裡登的」不一致的案子。**那些不一致本身就是高風險訊號。**
- **MDKP / MDTB（MRP 清單與例外訊息）** — 需求日更精確的來源。

## 三、十條規則的資料來源

| # | 規則 | 來源 | 是否需推導 |
|---:|---|---|---|
| 1 | 緩衝天數 | `purchase_req.need_date` − `po_schedule.committed_date` | ✅ 兩表 JOIN |
| 2 | 延遲幅度 | 信件解析結果 − `po_schedule.committed_date` | — |
| 3 | 單一來源 | `source_list` 合格供應商家數 ≥ 2 | ✅ COUNT |
| 4 | 下游已排定 | `purchase_req.downstream_scheduled` | ⚠️ **多數 ERP 沒有此欄位**，需來自 MES/APS 或銷售訂單確認日 |
| 5 | 料的關鍵性 | `material_master.std_lead_time_days` | LT 可直接取；**瓶頸料標記多為人工維護，很多公司沒維護** |
| 6 | **承諾強度** | **信件語意** | ❌ **ERP 結構上不可能有** |
| 7 | 累犯 | `po_change_log` 中 `committed_date` 的變更筆數 | ✅ COUNT |
| 8 | 延遲量佔比 | `po_item.qty` ÷ `purchase_req.period_demand_qty` | ✅ 計算 |
| 9 | 通知時機 | 信件收件時間 − `po_schedule.committed_date` | — |
| 10 | 可替代性 | `material_alternate` | ⚠️ 實務上常常沒維護 |

### 第 6 條是這個工具存在的理由

供應商在系統裡登的日期，跟他在信裡寫「大概月底吧，我再跟你確認」——
**在 ERP 看起來是同一個日期。**

**ERP 只存結果，不存語氣。** 而語氣裡藏著這個日期能不能信。
這是資料庫結構上補不起來的缺口，也是這個工具不會被 ERP 取代的部分。

## 四、真的要接時怎麼做

### 技術路徑（依資安可行性排序）

1. **IT 開唯讀 view** — 最常見。工具只讀不寫，資安審查最容易過。
2. **每日拋轉中繼表** — 若不允許直連生產庫。可接受，因為交期回覆本來就是日批次作業。
3. **OData / RFC / BAPI** — 需要較多權限與開發資源。

**不建議直連生產資料庫**：資安不會過，而且一個寫錯的查詢可能影響生產系統效能。

### 程式要改的部分

```
現在：  SqliteSource  →  讀 data/erp_sim.db
接 ERP：ErpSource     →  讀 IT 提供的 view / 中繼表
```

只需在 `src/adapters/` 新增一個 `DataSource` 子類別，實作三個方法：
`purchase_orders()` / `materials()` / `suppliers()`，
**規則、評分、介面一行都不用改。**

`src/adapters/base.py` 已定義好資料合約，且 `validate()` 會在載入時
檢查欄位是否齊全 —— 換來源最常見的失敗不是連不上，
而是「連上了但少一欄」，然後在下游某條規則裡爆掉。

### 驗收方式

`tests/test_adapters.py` 已經在驗證 CSV 與 SQLite 兩條路徑
推導出來的結果一致。**新增 ERP adapter 時應該沿用同一組測試**：
先用一份匯出的靜態快照跑一次，確認推導邏輯與 ERP 的理解沒有落差。

## 五、必須先跟 IT 與生管確認的事

寫在這裡是因為這些問題若沒先問清楚，程式寫得再漂亮也會白做：

1. **分批交貨怎麼處理？** 一個項次多筆排程行時，是要各自追蹤，
   還是只看最晚那筆？（本版取最晚，屬已知簡化）
2. **「下游已排定」的權威來源是哪裡？** ERP？MES？還是根本只存在生管的 Excel？
3. **瓶頸料標記有沒有人在維護？** 沒有的話，規則 5 要改用別的訊號。
4. **替代料主檔的維護率如何？** 沒維護的話，規則 10 形同虛設。
5. **變更文件有沒有開啟記錄？** 有些系統為了效能會關掉部分欄位的變更記錄。
6. **收貨紀錄能不能取得？** 這關係到未來能不能用資料校準權重 ——
   沒有它，這張評分卡永遠只能靠人調。
