# 設計決策與取捨

記錄「為什麼這樣做」以及「為什麼不那樣做」。
每一條都包含被否決的替代方案 —— 因為只講最後結果，看不出有沒有想過。

---

## 決策 1：不使用機器學習模型

**否決的方案**：訓練一個模型預測交期延遲機率。

**理由：**

1. **沒有歷史資料。** 在自己合成的資料上訓練一個模型去還原自己寫入的規則，
   是一個自我循環。面試或評審只要問一句「你的訓練資料哪來的」就會塌。
2. **第一版的內部工具，可解釋性遠比準確率重要。**
   生管不會信一個說不出理由的黑箱。工具排了一張清單，
   他問「為什麼這筆排第一」，如果答案是「模型說的」，他會用兩週就棄用。
3. **這張評分卡本身就是未來模型的 baseline。**
   等工具上線累積了三到六個月的「預警 vs 實際結果」，
   那時候才有資格談模型 —— 而且必須證明模型贏得過這張評分卡。
   沒有 baseline 的模型沒有意義。

**代價**：規則無法自動從資料中學習，權重要靠人調。
**緩解**：權重全部外部化到 `config.yaml` 並在 UI 上可即時調整，
讓調整的成本降到最低，且調整的過程本身會產生知識。

## 決策 2：分層解析，而非全部交給 LLM

**否決的方案**：每封信都呼叫 LLM。

**理由：**

1. **成本與延遲。** 一天幾百封信全部呼叫 API，同仁會嫌慢，IT 會關切預算。
2. **可重現性。** 規則層對同一封信永遠給同樣答案；LLM 不保證。
   格式化通知信佔了將近六成，這些信沒有理由讓它們變得不可重現。
3. **資料外流面。** 送出去的信件越少越好。能在本機處理完的就不要外送。

**這個決策必須被驗證，不能只是主張。**
因此 `src/evaluate.py` 做了分群對照實驗（結果見 README「評估」一節）：
規則層在 formal/semi/no_change 三群上是完美的，在 narrative/handcrafted 上歸零。
**實驗結果支持分層，而不是分層之後才去找理由。**

**代價**：兩套解析邏輯要維護，且需要一個信心分數的門檻參數。
**緩解**：門檻寫在 `config.yaml`，調整取捨的權力交給使用單位。

## 決策 3：規則層要「認真寫」，不能寫成稻草人

**否決的方案**：規則層只做最陽春的 regex，讓 LLM 看起來很強。

**理由**：那樣做出來的對照實驗沒有意義，甚至是誤導。
如果一個認真寫的規則層就能解決六成的信，那就**不應該**為那六成付 LLM 的錢。

因此規則層實作了：四種日期格式（ISO / DD-Mon-YYYY / 中文年月日 / M/D）、
欄位標籤角色判讀（Original ETA vs Revised ETA）、同列表格解析、
反向語意偵測（no change / 照原計畫）、以及**主動降低自己信心的機制**。

最後一項最重要：規則層必須知道自己什麼時候不該逞強。
偵測到相對日期、轉寄串、非表格式多單、退路措辭時，它會主動把信心壓低，
把案子讓給 LLM。**一個不會說「我不確定」的解析層，比解析錯更危險。**

## 決策 4：「承諾強度」獨立成一個欄位

**否決的方案**：只抽日期，把承諾強度當成 notes 裡的一句話。

**理由**：這是整個工具最重要的設計。詳見 README「① 讀信」一節。
簡言之 —— **AI 工具最大的風險不是答錯，是把不確定的事情講得很確定。**

把它獨立成欄位，才能：
- 成為影響評分的規則 6（且方向是「越不確定越該處理」）
- 觸發人工確認閘門
- 在 UI 上被明確標示
- 未來累積後成為供應商溝通品質的評鑑依據

---

## 決策 5：對位之後才判定延遲 / 提前

**否決的方案**：在解析階段就判定變更類型。

**理由**：單看信件無法知道新日期是提前還是延後 ——
必須跟採購單主檔的原承諾日比對。這是「解析」與「判斷」分工的具體體現：
**LLM 負責讀懂信，系統負責比對事實。**

把事實比對交給 LLM 是常見的錯誤：它可能算錯日期差，而且無法稽核。
凡是能用確定性程式算出來的，就不要交給模型。

---

## 決策 6：解析與評分分離

**否決的方案**：使用者調權重時重跑整個流程。

**理由**：重跑會再次呼叫 LLM API —— 又慢又花錢，而且同一批信重複送出去
也是不必要的資料外流。`pipeline.rescore()` 讓評分可以就地重算，
使用者才能放心地反覆拉滑桿試玩。

**這是「工具會不會被同仁真的用起來」的關鍵細節**：
如果每動一次滑桿要等十秒，沒有人會去調它，權重外部化的意義就消失了。

## 決策 7：合成資料，但把假設寫成程式碼

**否決的方案 A**：用 `np.random` 隨便灑數字。
**否決的方案 B**：找一個不相關的公開資料集硬套。

**理由**：真實資料屬營業秘密不可能公開；但亂灑資料等於沒有領域內容。
折衷是**把領域假設外顯化成可讀、可質疑、可修改的程式碼**
（`src/generate_data.py` 的每一段 `# 領域假設：` 註解）。

**這反而讓假設變得可被檢驗** —— 比拿真實資料但不說明處理方式更透明。

**代價**：任何在合成資料上的指標都不能外推到真實環境。
**緩解**：README 與 UI 上都明確標示這一點，且效益章節只使用
「無假設就能算出的數字」（壓縮率）與「附敏感度分析的假設」（工時）。

## 決策 8：手寫刁鑽案例，而非全部程式產生

程式產生的信件一定長得像模板，規則式 regex 全部都抓得到，
對照實驗會得出「不需要 LLM」的假結論。

因此另外手寫 10 封案例（`src/handcrafted_emails.py`），每一封對應
實際看過的溝通型態：轉寄串裡的舊日期、一封多單且結論不同、
分批交貨、相對日期、明確拒絕承諾、確認不變的陷阱、提前交貨。
每封都附人工標註答案，並用 `tags` 標記「難在哪」。

**這 10 封信是本專案領域含量最高的檔案之一。**

## 決策 9：節流、退避重試與結果快取（開發過程中被迫學到的）

**這一條不是事前設計，是踩坑後補的。誠實記錄。**

第一次執行對照實驗時，LLM 的欄位大面積掛零，看起來就是「模型解析不出來」。
實際去看原始錯誤內容，發現是 **HTTP 429 —— 免費層速率限制**。
如果當時直接下結論，會得到完全相反且錯誤的技術判斷。

補上的三件事（都在 `src/llm/provider.py`）：

| 機制 | 為什麼必要 |
|---|---|
| **節流** | 沒有節流，一次批次處理就會把整批請求打成 429，而失敗的那些看起來會像「模型不會解析」，導致錯誤的技術結論 |
| **退避重試** | 429/5xx 是暫時性錯誤，應退避重試而非當成解析失敗；且要**尊重服務商回傳的 `retryDelay`**，不要自己亂猜 |
| **結果快取** | 評估階段會對同一批資料反覆執行。沒有快取，每跑一次實驗就燒一次配額，結果還會因模型隨機性而不一致 |

補上之後，LLM 呼叫成功率從約 40% 變成 25/25。

`_is_retryable()` 刻意區分暫時性失敗（429/5xx/timeout）與真正的失敗
（400 prompt 有問題、404 模型名稱錯）—— 後者重試一百次也不會過，
只會白白消耗配額。

**開發期間還遇到模型下線**（`gemini-2.0-flash` 回 404 並指示改用新版本）。
這正是決策 2 的 provider 抽象與模型名稱外部化的價值：換模型只改 `.env`。

**已知限制**：快取目前沒有 TTL，永久有效直到 prompt 改變。
生產環境應加上期限，否則來源資料更新後仍會讀到舊的解析結果。

## 決策 10：把系統已知的原承諾日帶進 prompt

**這一條同樣是踩坑後才想通的，而且它是本專案最重要的架構修正。**

narrative 群一度兩層都是 0.000。查下去發現兩個問題疊在一起：

1. 標準答案存的是精確天數，但信裡寫「往後抓個兩週」——
   **那道題沒有答案**，任何模型都會零分。
2. 更根本的：信裡從來沒寫原承諾日。「往後兩週」是相對於哪一天？
   **那個資訊在我方系統裡，不在信裡。** 我卻只把 PO 號清單給模型，
   等於要求它猜一個不可能知道的數字。

修正後 prompt 帶入該供應商未結採購單的表格（單號／料號／原承諾日／需求日），
並明確規範推算基準：

| 說法 | 基準 |
|---|---|
| 「往後兩週」「N weeks beyond the original date」 | 該採購單的**原承諾日** |
| 「下個月中」「end of next month」 | **今天**（寫信當下） |

該群從 0.000 變成 1.000。

**這件事的一般化教訓**：LLM 的任務是「讀懂信件裡的變化」，
系統的任務是「提供事實基準」。把系統已有的事實藏起來不給模型，
再抱怨模型算不出來，是設計者的錯，不是模型的錯。

> 評估資料的瑕疵會產生錯誤的技術結論，而錯誤的技術結論會導致錯誤的架構決定。
> 看到一個很差的數字，第一件事應該是懷疑自己的量尺。

## 決策 11：工具永不自動寫回 ERP、永不自動寄信

理由見 README「② 排序」一節與 `docs/操作指引.md`。

這不是保守，是責任分配問題：**交期資料錯誤的代價由下游整條排程承擔**，
而工具無法承擔那個代價，所以它不該擁有那個權限。

## 決策 12：物料智能檢索採「語意檢索 ＋ 識別碼釘選」，而非混合檢索

**這一條是評估推翻原本設計的結果。**

原本的設計是業界文章常見的建議：詞彙檢索與語意檢索以 RRF 合併。
24 題、六種配置的評估（`src/rag/evaluate_rag.py`）結果：

| 配置 | Hit@3 |
|---|---:|
| 純語意檢索 | 0.917 |
| 混合檢索 | 0.792 |
| 混合 ＋ 識別碼釘選（原本的設計） | 0.833 |
| **語意 ＋ 識別碼釘選（現行）** | **0.958** |

混合檢索反而比純語意檢索差。查看答錯的題目後發現兩個原因：

1. 字元 n-gram 的詞彙檢索，在中文換句話說的六題**全部失敗**
   （「缺了沒辦法找別家救」與卡片上的「是否有已認證二源：否」沒有共同字詞）
2. RRF 讓兩路等權合併，弱的一路把強的一路的正確答案往後推
   （「哪家供應商最常延遲交貨」語意檢索排第 1，混合後掉到第 8）

識別碼釘選則確實有用：它解決了純語意檢索唯一答錯的識別碼題。
「PO-2026-04278 的供應商靠得住嗎」的答案在供應商卡上，不在採購單卡上；
向量不知道兩張卡有關，但資料結構知道。

**被否決的替代方案**：調整 RRF 的權重讓語意檢索佔比較高。
那樣也許能讓分數好看，但就是在針對 24 題調參數。
改用「語意 ＋ 釘選」的理由是結構性的：中文字詞比對不懂換句話說、
精確識別碼不該交給向量比對。

**詞彙檢索沒有刪掉**，它是沒有 API 金鑰時的備援（Hit@3 0.583，識別碼題全對）。

**已知風險**：題目由作者撰寫、僅 24 題，存在過度擬合的可能。

## 決策 13：知識庫切塊依資料形狀，並預先建立摘要卡

**被否決的方案**：所有內容一律每 500 字切一段。

結構化資料依實體切：一張採購單被切成兩半，前半有單號、後半有交期，
兩段單獨都沒用。文件依標題切，並在每段前面補上出處路徑。

**另外預先算好排名類的摘要卡。** 這是 RAG 最容易被忽略的限制：
**檢索做不了聚合。** 問「哪家供應商準交率最差」時，檢索只會撈出幾張相似的供應商卡，
模型只能從那幾家裡挑一個最差的 —— 答案看起來很有自信，卻可能是錯的。
prompt 也明確規定：排名問題只能使用摘要卡的排序，不可自行比較。

## 決策 14：回答要驗證出處，不只是要求出處

prompt 要求模型每個事實都標註出處，但**要求不等於做到**。
程式另外檢查模型引用的卡片編號，是否真的在提供給它的參考資料裡。

開發時第一次試跑就抓到：模型引用了 `[SUP:SUP-S01]`，
但那次檢索根本沒撈到那張卡。那句話是模型根據摘要卡推論出來、再掛上一個看似合理的出處。

引用不存在的出處時，介面會顯示警告並請使用者以原始資料為準。

## 決策 15：公開部署時以種子快取與工作階段額度保護 API 配額

**被否決的方案 A**：訪客開啟網頁時即時呼叫 API。
冷啟動要解析 25 封信、建立語意索引（本機首次約需數分鐘），訪客不會等；
而且每位訪客都在消耗配額。

**被否決的方案 B**：公開版完全關掉 LLM。
那樣展示的就不是這個工具真正的樣子。

**採用的做法**：
- 把「內容可重現」的結果預先算好一併部署（`demo_cache/`）。
  資料產生器使用固定亂數種子，prompt 每次相同，快取鍵在雲端對得上。
  以封鎖網路的乾淨副本驗證，冷啟動的 API 呼叫次數為 0
- 訪客問範例以外的問題才即時呼叫，每次工作階段上限 20 次，只計算未命中快取的呼叫
- 額度用完時工具照常可用：檢索改列原始資料、回信草稿改用模板

**踩坑紀錄**：第一次建立語意索引時固定每批 100 張卡，一批約 2.4 萬字，
直接超過每分鐘 token 上限而失敗；重試又在同一分鐘內疊加額度。
改為依字數切批後解決。

## 已知限制（完整清單見 README「已知限制」）

最需要被指出的三項：

1. **分批交貨只取最晚一批。** 實務上很常見，正確處理需要拆分採購單行項目。
2. **封測段與載板段沒有專屬規則。** 作者實務在 wafer 段，那兩段沒有把握，不硬寫。
3. **價格與商務條款完全未處理。** 作者是物料企劃不是採購，
   階梯價、NRE、長約、匯率、Incoterms 沒有實務基礎，
   需與採購同仁訪談後才敢動。
